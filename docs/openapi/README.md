# Generated OpenAPI Documents

One OpenAPI document per HTTP surface of GCO, generated rather than written by
hand: the four FastAPI services describe themselves, the two AWS API Gateways
are read out of their synthesized CDK stacks, and the in-cluster Gateway (the
internal ALB) is composed from its HTTPRoute and the service documents.

| Document | Surface | Generated by |
|----------|---------|--------------|
| [`api-gateway-global.json`](api-gateway-global.json) | The global API Gateway (`<project>-global-api`): the SigV4 front door — `/api/v1/{proxy+}`, `/api/v1/global/*`, `/inference/{proxy+}`, `/studio/*` — with each route's authorization, integration, Lambda backend, hop chain and deployment condition | `scripts/generate_api_gateway_openapi.py` (in-process CDK synthesis) |
| [`api-gateway-regional.json`](api-gateway-regional.json) | The per-region API Gateway bridge (`<project>-regional-api-<region>`): the same catch-alls through VPC Lambdas, the aggregator-only resource policy and the statements `regional_api_enabled` adds | `scripts/generate_api_gateway_openapi.py` |
| [`cluster-gateway.json`](cluster-gateway.json) | The internal ALB — Kubernetes Gateway `gco-system/gco-gateway`: every operation its HTTPRoute actually delivers, tagged with the backend Service, plus the paths a Service serves but never receives and the Services that are not on the ALB | `scripts/generate_cluster_gateway_openapi.py` (HTTPRoute manifest ∘ service documents) |
| [`manifest-processor.json`](manifest-processor.json) | `manifest-processor` — the control plane: manifests, jobs, the global job queue, templates, webhooks, cost reporting | `scripts/generate_openapi.py` (FastAPI `app.openapi()`) |
| [`inference-proxy.json`](inference-proxy.json) | `inference-proxy` — `/inference/*` proxying to deployed model endpoints | `scripts/generate_openapi.py` |
| [`health-monitor.json`](health-monitor.json) | `health-monitor` — cluster health, metrics, and status | `scripts/generate_openapi.py` |
| [`cost-monitor.json`](cost-monitor.json) | `cost-monitor` — cluster-internal `/internal/*` cost reporting | `scripts/generate_openapi.py` |

These are committed so the API surface is reviewable in a diff: a pull request
that changes a route, a parameter, or a request model shows the schema change
alongside the code, and a pull request that adds an API Gateway method or an
HTTPRoute rule shows the front door change the same way. The gateway documents
carry `x-gco-*` extensions (`x-gco-source`, `x-gco-backend`, `x-gco-route`,
`x-gco-condition`, …) that record what a plain OpenAPI document cannot: which
Lambda receives a route, the hops to the Service that answers, and the
deployment condition a route depends on.

Two human-facing renderings are generated from them and kept in lockstep by
`python diagrams/generate.py --check`:

- **Spec sheets** — one Markdown page per document under
  [`diagrams/api_specs/`](../../diagrams/api_specs/README.md) (endpoint table,
  parameters, request bodies, responses, component schemas; for the gateways
  also servers, deployment, routing and security-scheme sections), also served
  as the wiki's [API reference](https://aws-solutions-library-samples.github.io/global-capacity-orchestrator-on-aws/api/).
  The catalogue index embeds the
  [interaction diagram](../../diagrams/api_specs/README.md#how-the-surfaces-fit-together)
  drawn from these documents.
- **Swagger UI** — a Swagger console per document (FastAPI's own `/docs` page
  for the services), built by `pages.yml` into the project site at
  [`/swagger/`](https://aws-solutions-library-samples.github.io/global-capacity-orchestrator-on-aws/swagger/)
  from these documents with a self-hosted `swagger-ui-dist`.

## Regenerating

```bash
python scripts/generate_openapi.py                          # rewrite the service documents
python scripts/generate_api_gateway_openapi.py              # re-synthesize the API Gateway documents
python scripts/generate_cluster_gateway_openapi.py          # recompose the cluster gateway document
python diagrams/generate.py --api-only                      # re-render the spec sheets and the diagram
python diagrams/generate.py --check                         # fail if any sheet is stale
```

Each generator takes `--check` to fail without writing when its documents are
stale. The checks run as part of the test suite:
[`tests/test_api_docs_coverage.py`](../../tests/test_api_docs_coverage.py) for
the service documents (it also asserts that every live route is described in
[`../API.md`](../API.md)),
[`tests/test_api_gateway_openapi.py`](../../tests/test_api_gateway_openapi.py)
for the API Gateway documents (a fresh in-process synthesis of both stacks) and
[`tests/test_cluster_gateway_openapi.py`](../../tests/test_cluster_gateway_openapi.py)
for the cluster gateway. A route or rule added without regenerating fails
there. The API Gateway generator needs the CDK toolchain (`pip install -e
".[cdk]"` and Node for jsii); the other two need nothing beyond the project's
Python dependencies.

## Scope

FastAPI's own `/docs`, `/redoc`, and `/openapi.json` routes are excluded — they
are interactive documentation, not part of the API contract, and no API Gateway
forwards them. The Prometheus `/metrics` route is also absent because it is
mounted as a plain Starlette route and carries no OpenAPI schema; it is
documented in [`../API.md`](../API.md) instead.

The API Gateway documents describe the front doors as API Gateway sees them —
greedy `{proxy+}` catch-alls, not the operations behind them; follow an
operation's `x-gco-backend` hops to the service documents for those. The
cluster gateway document is derived from the service documents, so it repeats
their schemas; what is new in it is the routing decision per path. The
Mooncake prefill/decode proxy runs from a ConfigMap-hosted application and has
no document here; it is documented in [`../API.md`](../API.md).

## Using them

Point any OpenAPI-aware tool at a document to generate a client. The container
image needs nothing on your host beyond the runtime GCO already requires
(Docker, [Finch](https://runfinch.com/), or [Podman](https://podman.io/docs)):

```bash
mkdir -p ~/gco-client

docker run --rm \
  -v "$PWD/docs/openapi:/spec:ro" \
  -v "$HOME/gco-client:/out" \
  openapitools/openapi-generator-cli:v7.24.0 \
  generate -i /spec/manifest-processor.json -g python -o /out
```

That produces one API class per tag group — jobs, job queue, manifests,
templates, webhooks, cost, health — plus a model per request schema.

Two things to know before changing the command:

- **The output path must be inside a directory your runtime shares with the
  container.** Finch and Podman run a VM, so a bind mount of `/tmp` silently
  writes inside the VM and leaves the host directory empty. Paths under `$HOME`
  are shared by default, which is why the example writes there.
- **`npx @openapitools/openapi-generator-cli` needs a Java runtime.** The npm
  package is a wrapper that downloads a JAR and shells out to `java`, so without
  a JRE on your `PATH` it fails with "Unable to locate a Java Runtime". Use the
  container above, or install a JRE first.

Generated clients handle request shapes only. Every request still needs AWS IAM
SigV4 signing against the API Gateway host; see
[Authentication](../API.md#authentication) and the
[client examples](../client-examples/README.md).
